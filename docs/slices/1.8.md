# Slice 1.8: Weighted fit score

## Problem

The fit score is one number the model picks with no rubric, so the same resume and posting score differently from run to run (66 one time, 68 the next). Gaps are capped at five, so a posting with eight unmet requirements shows five, and several distinct gaps get squeezed into one bullet. Nothing says which gaps define the role and which are nice-to-haves. A user can't tell whether a revision actually improved the fit, or which gap to fix first.

## Acceptance criteria

1. Given a posting and a resume, when the fit is scored, then the model returns every requirement it finds, each with a weight (core, required, preferred), a status (met, partial, missing) and the resume evidence, and there is no cap on how many.
2. Given those requirements, when the score is computed, then it comes from code, not the model: weights core 3, required 2, preferred 1; credit met 1, partial 0.5, missing 0; score = earned / possible, as a whole percentage. Any score the model returns is ignored.
3. Given requirements with unknown weights or statuses, when the score is computed, then those rows are left out of the score instead of breaking it.
4. Given the scored requirements, when gaps are listed, then every partial or missing requirement appears, core first, then required, then preferred, each labeled with its weight and status.
5. Given a model reply with no usable requirements, when the fit is scored, then the result is a plain error, not a score of 0.
6. Given a scored result, when the app shows it, then it shows the hiring-manager impression (how the resume reads overall for this role) and a table of every requirement next to the existing score, strengths, gaps and suggestions.

## Out of scope

- Structured outputs (slice 1.1). This keeps `_parse_json`.
- Changing the keyword report or the generators.

## Risks

- **Personal data:** none new. Same resume and posting, same single call.
- **Truthfulness:** scoring generates no resume text. The evidence field asks for a resume phrase; it is shown to the user, never written into a document.
- **Cost:** same single call. The output is longer (one row per requirement), roughly 1 to 2K more output tokens.
- **Untrusted input:** the posting and resume stay in the user message. Model-supplied text is shown through `st.markdown` and `st.dataframe` as before, with no `unsafe_allow_html`.
